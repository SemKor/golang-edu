# Урок 4 - Транспортные протоколы. Потокобезопасные структуры. Логирование.

Протокол – это набор правил, определяющий, как узлы сети должны передавать данные друг другу. </br>
Вы скорее всего слышали про высокоуровневые протоколы – HTTP, SSH, FTP, SMTP, SOAP. </br>
В сфере телекоммуникаций огромное количество протоколов, каждый из которых решает какую-то свою задачу. </br>
Из-за того, что их много, есть даже специальные модели, определяющие «уровни протоколов». </br>
Если представить, что ваше сообщение, – это конфета, то протоколы в каком-то плане играют роль обёрток для этой конфеты.</br>

Интернет работает за счёт коммутации пакетов. Основной его стек – TCP/IP. </br> 
Два главных протокола транспортного уровня этого стека – TCP и UDP.</br>
В данном уроке мы рассмотрим прикладной протокол - HTTP, транспортные протоколы TCP и UDP, и то как Golang </br>
предлагает с ними работать внутри себя. </br>

### UDP
Этот протокол используется для «связи без установки соединения» (connectionless communication – пер.). </br>
Один узел сети просто отсылает пакеты, адресуя их другому узлу. Отправитель не знает ничего о том, </br>
готов ли получатель к приёму пакетов, и вообще, существует ли этот получатель. Отправитель также не ждёт </br>
какого-либо подтверждения о том, что получатель принял предыдущие пакеты.</br>
Пакеты, передаваемые с помощью UDP, иногда называются датаграммами. Этот термин обычно используется тогда, </br>
когда важно подчеркнуть, что пакет передаётся без установки соединения.</br>
Заголовок UDP-пакета состоит из 8 байт, которые включают в себя:</br>

* порт отправителя
* порт получателя
* длину датаграммы
* контрольную сумму

### TCP
Если UDP простой и не требующий установки соединения, то TCP – сложный и требующий. </br>
Перед тем, как начать передачу данных, клиент и сервер должны подключиться друг к другу и договориться о том, </br>
как они будут осуществлять эту самую передачу.</br>
В отличие от датаграмм в UDP, пакеты, создаваемые TCP, называются сегментами.</br>
А вот, некоторые из тех задач, что решает TCP во время передачи данных:</br>

* Убеждается в том, что сегменты доставлены в нужном порядке.
* Убеждается в том, что они вообще доставлены.
* Контролирует поток пакетов, чтобы не перегружать им узлы сети.

Работы много, а потому и заголовок у TCP как минимум 20 байт, а то и больше. Он включает в себя:</br>

* порт отправителя
* порт получателя
* порядковый номер
* номер подтверждения
* длину заголовка
* флаги
* размер окна
* контрольную сумму
* указатель важности
* дополнительные опции

### HTTP
Мы видим HTTP в каждой ссылке: http://google.com/. Что это значит? HTTP - это протокол передачи гипертекста. </br> 
Грубо говоря, это тип разметки, которая добавляется в текстовые документы для определенного отображения текста.</br> 
В стеке протоколов HTTP находится на прикладном уровне. Он использует под собой протокол транспортного уровня - TCP.</br>
Режим работы HTTP - запрос-ответ: клиент посылает серверу запрос на передачу web-страницы, после чего сервер пересылает </br>
эту страницу клиенту. При этом нет жестко заданного формата пакетов: используется текстовый режим.</br>

### Реализация в Golang
Среди стандартных пакетов в GO есть  **net**, позволяющий работать как со стороны сервера, так и клиента по протоколам UDP и TCP.</br>
Также есть более прикладной пакет **net/http**, для протокола HTTP.</br>
Простейший способ запустить HTTP-сервер — вызвать http.ListenAndServe: </br>
```go
package main

import (
	"log"
	"net/http"
)

type Handler struct {}

func (h *Handler) ServeHTTP(w http.ResponseWriter, req *http.Request){
	_,err := w.Write([]byte("hello world!"))
	if err != nil {
		log.Println(err)
	}
}

func main() {
	log.Println(http.ListenAndServe("localhost:8080", &Handler{}))
}
```

Здесь мы запуcтили сервер на порту 8080. </br>
Вторым параметром мы указали переменную, удовлетворяющую интерфейсу http.Handle,  </br>
который требует функции ServeHTTP(w http.ResponseWriter, req *http.Request).  </br>
Данная функция будет принимать все запросы к нашему серверу:
```text
curl localhost:8080/someurl
hello world!

curl localhost:8080/secondurl
hello world!
```
Также мы можем сконфигурировать наш сервер обрабатывать конкретный URL: </br>
```go
package main

import (
	"log"
	"net/http"
)

func main() {
	http.HandleFunc("/hello", func(w http.ResponseWriter, req *http.Request){
		_,err := w.Write([]byte("hello"))
		if err != nil {
			log.Println(err)
		}
	})

	log.Println(http.ListenAndServe("localhost:8080", nil))
}

```

Как это работает? Когда мы добавляем функции обработичики, они сохраняются в структуру net/http.DefaultServeMux,</br>
которая хранит все обрабатываемые URL-ы и функции для их обработки.</br>
Стандартный роутер обладает простейшей функциональностью — </br>
при запросе явно сопоставляет URL запроса с каждым зарегистрированным обработчиком. </br>
Возможно, вы захотите обрабатывать не конкретные URL-ы, а некоторые шаблоны. </br>
Например, /hello/{page}, где page — параметр из строки запроса (номер страницы). </br>
Для реализации этого нам потребуется нестандартный роутер.
Подробнее о нестандартных роутерах мы поговорим в следующем уроке, а пока обратим внимание на варианты,</br>
как создать TCP или UDP подключение:</br>
```go
package main

import (
	"net"
)

func main() {
	conn1, err := net.Dial("tcp", "localhost:8080") // Dial by TCP to the server
	conn2, err := net.Dial("udp", "localhost:8080") // Dial by UDP to the server
	listener1, err := net.Listen("tcp", "localhost:8080") // Start server to listen to TCP connections 
	listener2, err := net.Listen("udp", "localhost:8080") // Start server to listen to UDP connections
}
```

### Задание
Вместе с данным уроком представлен шаблон приложения, который необходимо реализовать.</br>
Задачей будет реализация приложение-чата, умеющего работать в двух режимах работы - клиент чата и сервер, обслуживающий чат.</br>
Клиент перед отправкой сообщения должен добавлять к нему префикс - имя клиента и двоеточие.</br>
Ввод сообщений в клиенте должен осуществляться через prompt, а отправка по переносу строки (нажатие enter). </br>
Режим работы приложения должен определяться в файле конфигурации. </br>
Обычно принято подобные файлы содержать в каталоге /etc. Также обратите внимание на каталог - internal.</br>
В Golang подобное наименование является ключевым словом, которое говорит компилятору о том, что все файлы, </br>
лежащие в каталоге будут являться неэкспортируемымы в случае, если мы захотим данный модуль использовать как подключаемою библиотеку.</br>

**Серверу** необходимо обрабатывать подключения и для каждого подключения при получении от него сообщения - </br> 
отправлять его всем клиентам (шаблон fan-out).</br>
Для этого нам придется воспользоваться структурой **sync.Map** - то же, что и </br>
**map** только **потокобезопасной**, чтобы хранить в ней все зарегистрированные сервером подключения.</br>
**Потоковая безопасность (англ. thread-safety)** — это концепция программирования, </br>
применимая к многопоточным программам. Код потокобезопасен, если он функционирует исправно при использовании его </br>
из нескольких потоков одновременно. В частности, он должен обеспечивать правильный доступ нескольких потоков к разделяемым данным.</br>
Так как код, рассылающий сообщения будет работать в горутинах для всех соединений сервера,</br>
то коллеция соединений станет разделяемым ресурсом между потоками.</br>
Предлагается писать все соединения в sync.Map, как генерировать уникальный ключ для записи - выбирайте сами.</br>
Также в шаблоне для обоих режимов присутствует задел на **Graceful Shutdown** - механизм, при котором приложение </br>
ожидает сигнала для завершения работы от системы чтобы перед тем как завершить свою работу освободить все ресуры.</br>
Пример:</br>
```text
done := make(chan os.Signal, 1) // создаем канал в который будем ожидать сигнал о завершении работы
signal.Notify(done, os.Interrupt, syscall.SIGINT, syscall.SIGTERM, syscall.SIGSTOP, syscall.SIGQUIT) // подписываемся на все интересующие нас сигналы
...
<-done // блокируемся в main-горутине, ожидая сигнала на завершение программы
```

Для организации в горутинах выбора передачи управления нам поможет ключевое слово **select**:
```go
package main

func main() {
	var done chan struct{}
    go func() {
		for {
			select {
			case <-done:
				return
			default:
				// other logic
			}
		}
    }()
	// ...
}
```
Здесь оно дает нам возможность выйти из бесконечного цикла при получении сигнала в канал. </br>

Также в приложение необходимо организовать **логирование** как вспомогательное - промежуточная печать,</br>
так и для обработки ситуаций в которых мы получаем ошибку.</br>
**Логирование** - фиксация и структурирование информации о работе программы в определенный поток вывода, например,</br>
стандарный вывод или файл.</br>
В Golang есть стандартный пакет для логгера, но он не обладает одним важнейшим свойством - </br>
у него отсутствуют уровни логирования. Так как логгер создают сами по себе нагрузку при работе с программой,</br>
а нам может быть необходимо писать множество отладочной информации, то очень важно иметь инструмент,</br>
в котором печать записей с отладочной информацией могла бы появляться только при необходимости.</br>
Тут на помощь и приходят уровни логирования - PANIC FATAL ERROR WARN INFO DEBUG и т.п. по приоритету слева-направо.</br>
В чем смысл? В том что при установке логгеру уровня ERROR все записи с уровнем "правее" проигнорируются.</br>
И только в ситуации когда нам понадобиться увидить дополнительную информацию, мы, перезапустив наше приложение с другим уровнем,</br>
увидим необходимую для отладки информацию.</br>
В данном уроке предлагается ознакомиться и использовать замечательный сторонний логгер **uber/zap**,</br>
функция для инициализации которого представлена в шаблоне в пакете **internal/logger**.
